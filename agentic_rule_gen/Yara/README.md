# YARA Rules

Generated by the ioc-yara-daily pipeline from public CTI reports (vendor research blogs, advisories, news).

## Layout

- `agentic/<family>_<id>/` — rules derived from a structured threat profile of one report, plus `profile.json` (every artifact with how the report evidences it) and `README.md` (source and per-rule rationale).
- `ioc-batch/` — exact file-hash rules (`IOC_*_Hashes`) for hashes that malware/intrusion reports publish as sample hashes. Reports can also list legitimate files they discuss (abused tools, drivers), so use these for hunting, not blocking.

## Quality gate

Every rule is checked automatically before it is published:

- **String provenance:** every string must be shown or stated by the report to exist in the binary (strings listing, decompilation or hex figure, or an explicit "hardcoded" statement). Each string carries a `// source:` comment. Values from IOC appendices, encrypted configs or runtime traffic are never YARA strings.
- **No compiled-away names:** enum, `#define`, constant and variable names are rejected.
- **Hash-gated values:** when the binary only compares a hash (CRC32, djb2, FNV, ROR13…), the rule uses the hash constant as little-endian hex, never the plaintext.
- **Classification:**
  - `$x`: unique, at least 8 bytes; may fire alone.
  - `$s`: supporting; needs combinations.
  - `$c`: constants; never fire alone.
  - `$g`: generic; never fire alone.
- **Behaviour tests:**
  - Each non-`$x` string is placed alone in a synthetic PE/ELF/Mach-O buffer and must not trigger the rule.
  - The rule must fire when all of its strings are present.
  - Rules fully covered by another rule are dropped.
- **No substring redundancy** inside a counted group. `all of` and `any of them` are not allowed.
- **Goodware scan:** `$x` strings that appear in a goodware corpus are removed.
- **Attribution:** features inherited from public tools (3snake, frp, Mimikatz…) go into `HKTL_` rules, not actor rules.
- **Strict mode (aimed at zero false positives):**
  - A string fires a rule alone only if it is a strong anchor: a typelib GUID or PDB path, a hex pattern of at least 8 bytes, a text string of at least 16 bytes, or a high-entropy key/salt of at least 10 bytes. Standard web/protocol text (browser User-Agents, CSP and security headers, HTTP request lines) never counts as an anchor, and neither do domains, URLs or IPs: legitimate software embeds the same service hosts.
  - No two weak strings may fire a rule together.
  - Every rule checks the file header and has a `filesize` bound.
  - Generic strings are not allowed.
- **Honesty:** no rule has been run against real samples, so every rule carries `status = "untested"`, `score <= 60`, a `test_result` saying why, and lists `unverified_strings`. Strictness lowers false positives at the cost of recall: some variants will be missed on purpose.

TLP:WHITE. Every rule's `meta.reference` points to the source report.

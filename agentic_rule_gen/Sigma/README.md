# Sigma Rules

Generated by the ioc-yara-daily pipeline from public CTI reports.

## Layout

- `agentic/<family>_<id>/` — one behaviour per rule (persistence, masquerading paths, loader command lines, C2 DNS/connections/URIs), plus `profile.json` and `README.md` for context.

## Quality gate

- **Spec compliance:** SigmaHQ spec v2 keys, Sigma taxonomy logsources and field names, and every selection referenced in `condition`.
- **Source check:** every artifact must appear in the source report (after refanging), so invented values never reach a rule.
- **False-positive control:** Sigma semantics apply (fields are ANDed, list values are ORed unless `|all`).
  - A selection is rejected if it can match on short or generic values alone (`bash`, `/tmp/`, `curl`, `setenforce 0`, …).
  - A selection is rejected if an OR-list mixes specific values with weak ones.
- **Attribution:** features inherited from public tools are titled as tool detections, not actor detections.
- **Strict mode (aimed at zero false positives):**
  - Every selection ANDs at least two specific fields, for example `Image` + `CommandLine`. The only single-field selections allowed are lists of attacker-owned domains, IPs or URLs, at most one rule per kind per report.
  - Shared infrastructure (`workers.dev`, `github.io`, `amazonaws.com`, `cloudfront.net`, ngrok, Telegram, Discord, …) and private or reserved IPs are rejected.
  - `level` is medium or higher.

`status: experimental` throughout. TLP:WHITE. Every rule's `references` points to the source report.
